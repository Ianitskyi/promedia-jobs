# ProMedia Jobs

Вакансії із зарплатами в медіа, журналістиці, маркетингу, рекламі, PR, комунікаціях, контенті та суміжних креативних індустріях. Ініціатива ГО «ПроМедіа».

🔗 Заплановано: **jobs.promedia.report** (поки без DNS/хостингу — див. «Статус» нижче)

## Статус

Це **клікабельний прототип**, аналогічний за підходом до інших демо-проєктів команди (`postup`, `ratings.promedia.report`): статичні HTML/CSS/JS-сторінки без бекенду, дані вигадані (крім кількох реальних вакансій, доданих вручну — див. `js/data.js`), стан (власні вакансії роботодавця, профіль компанії, підписки шукачів на фільтр) — у `localStorage` браузера. Кнопки реєстрації та надсилання форм показують демо-сповіщення й нічого нікуди не надсилають.

Дизайн свідомо перевикористовує айдентику ПроМедіа (navy `#0d0c5c` + accent `#ffac33`, Playfair Display + Montserrat), уже застосовану на `ratings.promedia.report`.

**Сервіс навмисно спрощено до одного призначення: каталог вакансій.** Пошук роботи не потребує реєстрації, акаунта чи резюме на порталі — кандидат просто переглядає каталог і пише роботодавцю напряму на вказану пошту. Реєстрація потрібна лише роботодавцям, щоб додавати й керувати власними вакансіями. Кожна опублікована вакансія обов'язково містить зарплату (суму або діапазон), соціальний пакет і дату, до якої вона активна — без цього вакансія не проходить модерацію.

## Обмеження цього прототипу (репозиторій)

Через обмеження доступу сесії цей розділ додано у форматі, сумісному з наявними GitHub-репозиторіями команди, а не як окремий production-репозиторій із власним CNAME на `jobs.promedia.report`. Перед реальним запуском варто:

1. Створити окремий репозиторій (або окремий застосунок) саме під субдомен `jobs.promedia.report` — один репозиторій GitHub Pages обслуговує один CNAME, тож ділянка не може одночасно жити в репозиторії іншого субдомену.
2. Замінити статичний прототип на застосунок із реальним бекендом (розділ «Технічний стек» нижче).

## 1. Інформаційна архітектура та карта сторінок

```
Публічні (без входу):  index (= каталог), vacancy, company,
                        how-it-works, privacy, report, terms
Роботодавець:           employer-login, post-vacancy, employer-cabinet
                        (власні вакансії, профіль компанії з лого,
                         налаштування акаунта)
Адмін:                  admin (модерація вакансій, скарги, джерела
                         імпорту, журнал імпорту, аналітика)
```

Кожна вакансія доступна не більш ніж за 1–2 кліки з головної (фільтр/сортування → картка → деталі). Кандидатського акаунта в системі немає.

## 2. Ролі та права доступу

| Дія | Відвідувач (шукач роботи) | Роботодавець | Модератор | Адмін |
|---|---|---|---|---|
| Перегляд каталогу й карток вакансій | ✓ | ✓ | ✓ | ✓ |
| Написати роботодавцю (mailto, поза порталом) | ✓ | — | — | — |
| Створення/редагування власної вакансії | — | ✓ | — | ✓ |
| Модерація вакансій, скарги | — | — | ✓ | ✓ |
| Керування джерелами імпорту | — | — | — | ✓ |

Реєстрація існує лише для роботодавців. Один обліковий запис = один профіль компанії.

## 3. Структура бази даних (основні сутності та зв'язки)

```
users 1—1 employer_profiles ──< companies (employer_profiles.company_id)
companies 1—1 company_logo
employer_profiles / companies 1—< vacancies
skills, languages, regions — довідники, багато-до-багатьох із vacancies
sources 1—< imported_items ──1 vacancies (imported_items.vacancy_id, nullable для прямих вакансій)
sources 1—< import_logs
imported_items >—< duplicate_groups (одна вакансія — кілька підтверджених джерел)
users 1—< reminders
moderation_actions, reports, consents — прив'язані до vacancies/users
audit_logs — окремий журнал усіх адміністративних дій
```

Для `vacancies` і `employer_profiles` ведеться історія змін (append-only лог версій, а не перезапис).

## 4. Технічний стек (пропозиція для реальної реалізації)

- **Frontend:** Next.js (React) + TypeScript — SSR/SSG для SEO вакансій і сторінок компаній, українська локалізація за замовчуванням через `next-intl`.
- **Backend/API:** Node.js (NestJS) або Next.js API routes для MVP; REST або tRPC.
- **База даних:** PostgreSQL (реляційні зв'язки вакансія/область) + Redis для черг і кешу.
- **Файлове сховище:** S3-сумісне (Cloudflare R2 / AWS S3) для логотипів компаній, з антивірусною перевіркою при завантаженні.
- **Планувальник:** cron-воркер (BullMQ на Redis) для оновлення джерел імпорту, нагадувань про завершення строку, деактивації прострочених записів.
- **Пошук:** PostgreSQL full-text спочатку; за потреби — Meilisearch/Typesense для швидкого пошуку й фільтрів.
- **Авторизація:** email + пароль, підтвердження пошти, опційна 2FA (TOTP), CAPTCHA на реєстрації — лише для роботодавців.
- **Хостинг:** окремий проєкт/репозиторій із CNAME `jobs.promedia.report`, розгортання через Vercel/Netlify або власний VPS + reverse proxy.

### Автоматичне щоденне оновлення (реалізовано й перевірено на реальних даних)

`.github/workflows/daily-vacancy-import.yml` щодня о 05:00 UTC (і за ручним запуском) запускає `scripts/import-dsz-vacancies.js`, який:

1. Знаходить датасет «6. Перелік актуальних вакансій станом на дату» ДСЗ на data.gov.ua через CKAN API (`package_show`, з резервним пошуком за ключовими словами, якщо ID датасету зміниться) — це справжній датасет з організації «Державна служба зайнятості», 1300+ ресурсів (щомісячні знімки з 2018 року).
2. Перебирає ресурси від найновішого (CSV **і** XLS/XLSX — переважна більшість знімків саме в форматі Excel), завантажує кожен і бере перший, що реально має колонки назва посади + роботодавець + зарплата — той самий package_id інколи містить і сторонні звіти (наприклад, картки вже працевлаштованих осіб), тож найновіший файл не завжди підходить.
3. Excel-файли читає власний мінімальний парсер `scripts/xlsx-mini.js` без npm-залежностей — свідоме рішення: опублікована на npm версія пакета `xlsx` має незакриті вразливості (prototype pollution, ReDoS), а патчений білд SheetJS роздають лише зі свого CDN. Файл підтримує **два** реальні формати під розширенням .xls/.xlsx: справжній ZIP+XML `.xlsx` і — це виявилося тим, що реально роздає ДСЗ за 2025-2026 роки — "Excel XML Spreadsheet 2003" (SpreadsheetML), тобто звичайний текстовий XML-файл без жодного ZIP-контейнера, лише з .xlsx-розширенням для сумісності з Excel.
4. Для CSV — розпізнає кодування (частина файлів ДСЗ у windows-1251, не UTF-8) і роздільник (кома чи крапка з комою) автоматично; для SpreadsheetML XML кодування бере з `encoding=` у самому XML-пролозі.
5. Розпізнає потрібні колонки за списком синонімів заголовків (назва вакансії, роботодавець, область, зарплата, опис) — без жорстко прописаних індексів, бо державні набори даних періодично міняють формат.
6. Залишає лише вакансії, дотичні до тем сайту (медіа, PR, маркетинг, SMM, журналістика тощо — ключові слова в `TOPIC_KEYWORDS`, зі співставленням на межі слова, і винятками на кшталт "промислов"/"виробнич" для державних назв посад, які збігаються за словом, але не за суттю) **і** з указаною зарплатою — те саме правило, що діє для прямих вакансій роботодавців.
7. Прибирає дублікати в межах одного запуску (масові вакансії в держдатасеті часто повторюються кількома однаковими рядками) і перезаписує `js/imported-vacancies.js` (максимум 20 вакансій за раз, `id` — стабільний хеш назва+компанія+область, щоб та сама вакансія не з'являлась двічі при повторному імпорті).
8. Комітить і пушить файл у `main`, якщо він змінився.

Якщо жоден із перевірених ресурсів не підходить (немає потрібних колонок) — скрипт падає з помилкою і **не** переписує `js/imported-vacancies.js`: сайт ніколи не покаже вигадані чи неправильно розібрані дані, лишається вчорашній стан.

Є також окремий ручний діагностичний workflow `.github/workflows/dsz-search-diagnostic.yml` (`scripts/dsz-search-diagnostic.js`) — нічого не записує, лише виводить у лог список датасетів data.gov.ua за кількома пошуковими запитами: корисно, якщо ДСЗ колись перейменує чи перенесе основний датасет.

Оскільки в репозиторію поки немає реального хостингу (див. «Статус» на початку), цей пайплайн зараз лише тримає дані в git-репозиторії свіжими щодня — на живому сайті вакансії з'являться, коли з'явиться реальний деплой з автооновленням при пуші в `main`.

## 6. Виявлення дублікатів

Псевдоалгоритм:

```
score = 0
+ 40, якщо нормалізовані назва посади + компанія збігаються (fuzzy match, схожість ≥ 0.85)
+ 20, якщо місто збігається
+ 15, якщо зарплатний діапазон перетинається
+ 15, якщо зовнішній ідентифікатор чи посилання вже зустрічались
+ 10, якщо дата публікації в межах ±3 днів
якщо score ≥ 70 → одна duplicate_group; обираємо основний запис:
  пряма вакансія роботодавця > вакансія з офіційного API > вакансія з дозволеного парсингу
```

Усі підтверджені джерела одного дубліката зберігаються в `imported_items`, але публічно показується один запис.

## 7. Обов'язкові поля вакансії

ProMedia Jobs публікує лише вакансії, що проходять модерацію з такими обов'язковими полями (перевіряються у формі `post-vacancy.html` перед відправкою):

- **Зарплата** — стартова сума або діапазон (наприклад, нижча на випробувальний термін і вища після нього). Вакансії без зарплати не приймаються.
- **Країна** (за замовчуванням — Україна) **і область** — область обов'язкова лише для вакансій в Україні; для інших країн деталізація локації йде прямо в текст оголошення.
- **Соціальний пакет** — перелік перків (медстрахування, харчування, англійська, психолог або свій варіант) і обов'язковий формат оформлення (трудова / цивільно-правова угода / ФОП / інший формат).
- **Дата, до якої вакансія активна.**
- **Контактна пошта** для кандидатів (подача — напряму, поза порталом).

Тип зайнятості й мінімальний досвід (років) — теж частина форми; досвід (`experienceYears`) додатково використовується для сортування каталогу.

## 8. Backlog і етапи (мапується на MVP-список зі специфікації)

**Етап 0 — фундамент:** авторизація роботодавця, профіль компанії, довідники (зокрема області), база даних.
**Етап 1 — контент:** створення вакансій вручну, каталог, фільтри й сортування, сторінки компаній.
**Етап 2 — строки:** обов'язкова дата завершення, архівація, нагадування, самостійне редагування дедлайну роботодавцем.
**Етап 3 — взаємодія:** редагування/дублювання/зняття з публікації, чернетки.
**Етап 4 — імпорт:** ✅ автоматичний конектор ДСЗ (щоденний, GitHub Actions) реалізовано; далі — ручний імпорт адміністратором для решти джерел, виявлення дублікатів між ними.
**Етап 5 — модерація й адмінка:** черга модерації, скарги, базова аналітика.

Кожен наступний етап залежить від фундаменту (Етап 0) і моделі даних вакансії (Етап 1).

## 9. Критерії приймання (витяг)

- Роботодавець створює, редагує, дублює й знімає з публікації власну вакансію; без реєстрації робити це не можна.
- Вакансія без зарплати, соцпакета або дати завершення не приймається на модерацію.
- Вакансії автоматично архівуються після вказаної дати, з нагадуванням заздалегідь; роботодавець може самостійно змінити дату завершення в будь-який момент.
- Шукач роботи бачить каталог і сторінку вакансії без реєстрації й пише роботодавцю напряму — портал не зберігає резюме чи листування кандидатів.
- Імпортовані вакансії завжди містять посилання на першоджерело; дублікати не створюють окремих карток.
- Усі адміністративні дії фіксуються в журналах.

## 10. План тестування (напрямки)

- **Юніт-тести:** валідація обов'язкових полів форми вакансії (зарплата, соцпакет, дата завершення), дедуплікація, сортування каталогу за зарплатою/досвідом.
- **Інтеграційні:** цикл імпорту джерела (fetch → normalize → duplicate-check → moderation).
- **E2E (golden path):** реєстрація роботодавця → профіль компанії з лого → вакансія (усі обов'язкові поля) → модерація → публікація → вакансія видима в каталозі з правильними фільтрами. Анонімний відвідувач: фільтрує каталог → відкриває вакансію → пише на контактну пошту.
- **Доступність:** контраст, клавіатурна навігація, alt-тексти, коректна робота зі скринрідерами (WCAG 2.1 AA).
- **Юридичний огляд перед запуском:** політика конфіденційності, згода на обробку даних, умови використання кожного джерела імпорту.
