# ProMedia Jobs

Пошук роботи та працівників у медіа, журналістиці, маркетингу, рекламі, PR, комунікаціях, контенті та суміжних креативних індустріях. Ініціатива ГО «ПроМедіа».

🔗 Заплановано: **jobs.promedia.report** (поки без DNS/хостингу — див. «Статус» нижче)

## Статус

Це **клікабельний прототип**, аналогічний за підходом до інших демо-проєктів команди (`postup`, `ratings.promedia.report`): статичні HTML/CSS/JS-сторінки без бекенду, дані вигадані й лежать у `js/data.js`, стан («збережено», підписки, відгуки) — у `localStorage` браузера. Кнопки оплати, реєстрації та надсилання форм показують демо-сповіщення й нічого нікуди не надсилають.

Дизайн свідомо перевикористовує айдентику ПроМедіа (navy `#0d0c5c` + accent `#ffac33`, Playfair Display + Montserrat), уже застосовану на `ratings.promedia.report`.

## Обмеження цього прототипу (репозиторій)

Через обмеження доступу сесії цей розділ додано у форматі, сумісному з наявними GitHub-репозиторіями команди, а не як окремий production-репозиторій із власним CNAME на `jobs.promedia.report`. Перед реальним запуском варто:

1. Створити окремий репозиторій (або окремий застосунок) саме під субдомен `jobs.promedia.report` — один репозиторій GitHub Pages обслуговує один CNAME, тож ділянка не може одночасно жити в репозиторії іншого субдомену.
2. Замінити статичний прототип на застосунок із реальним бекендом (розділ «Технічний стек» нижче).

## 3. Структура бази даних (основні сутності та зв'язки)

```
users 1—1 candidate_profiles
users 1—1 employer_profiles ──< companies (employer_profiles.company_id)
candidate_profiles 1—< resumes
employer_profiles / companies 1—< vacancies
vacancies >—< categories (через vacancy_categories)
resumes >—< categories (через resume_categories)
categories, skills, languages, locations — довідники, багато-до-багатьох із vacancies/resumes
vacancies 1—< applications >—1 resumes
applications 1—1 application_statuses (журнал зміни статусу)
sources 1—< imported_items ──1 vacancies (imported_items.vacancy_id, nullable для прямих вакансій)
sources 1—< import_logs
imported_items >—< duplicate_groups (одна вакансія — кілька підтверджених джерел)
users 1—< subscriptions 1—1 subscription_filters
users 1—< saved_vacancies 1—1 saved_item_notes, saved_item_statuses
resumes >—< vacancies через matches 1—1 match_scores, match_reasons, match_feedback
users 1—1 recommendation_settings
vacancies / resumes 1—< promoted_items
users 1—< orders 1—1 payments, refunds; orders >—1 promo_codes; payments 1—1 invoices
users 1—< notifications, notification_preferences, reminders
moderation_actions, reports, consents, uploaded_files — прив'язані до vacancies/resumes/users
```

## 4. Технічний стек (пропозиція для реальної реалізації)

- **Frontend:** Next.js (React) + TypeScript — SSR/SSG для SEO вакансій і сторінок компаній, українська локалізація за замовчуванням через `next-intl`.
- **Backend/API:** Node.js (NestJS) або Next.js API routes для MVP; REST або tRPC.
- **База даних:** PostgreSQL (реляційні зв'язки вакансія/резюме/категорії критичні) + Redis для черг і кешу.
- **Файлове сховище:** S3-сумісне (Cloudflare R2 / AWS S3) для CV та логотипів, з антивірусною перевіркою при завантаженні.
- **Парсинг CV:** окремий воркер (наприклад, на основі `pdf-parse`/`mammoth` для тексту + евристики секцій; за потреби — LLM-асистована структуризація з обов'язковим переглядом користувачем, без автогенерації фактів).
- **Планувальник:** cron-воркер (BullMQ на Redis) для оновлення джерел імпорту, нагадувань про завершення строку, деактивації прострочених записів.
- **Пошук:** PostgreSQL full-text спочатку; за потреби — Meilisearch/Typesense для синонімів і швидкого пошуку резюме/вакансій.
- **Платежі:** LiqPay / WayForPay / Fondy (гривня); токенізація карт на боці провайдера — ProMedia Jobs не зберігає повні дані карток.
- **Авторизація:** email + пароль, підтвердження пошти, опційна 2FA (TOTP), CAPTCHA на реєстрації.
- **Хостинг:** окремий проєкт/репозиторій із CNAME `jobs.promedia.report`, розгортання через Vercel/Netlify або власний VPS + reverse proxy.

## 5. Архітектура імпорту

Кожне джерело підключається через окремий **connector/adapter** із єдиним інтерфейсом (`fetchList()`, `fetchDetail()`, `normalize()`), що віддає дані у стандартну проміжну схему перед збереженням в `imported_items`. Якщо той самий запис підтверджується кількома джерелами одночасно, вакансія отримує масив `sources: [{name, url}]` замість дубльованої картки (див. розділ 6).

| Джерело | Спосіб | Правовий статус |
|---|---|---|
| Єдиний портал вакансій ДСЗ (jobportal.dcz.gov.ua) | Офіційні відкриті дані держави (data.gov.ua, вивантаження XML/CSV) | **Дозволено** — Закон «Про доступ до публічної інформації»: вільне використання за умови посилання на джерело |
| Work.ua | Прямого публічного API для агрегаторів немає; сам сайт входить до партнерів порталу ДСЗ, тож частина його вакансій доступна опосередковано через відкриті дані ДСЗ | **Не підтверджено напряму** — пряме API Work.ua лише для роботодавців (власні вакансії), не для стороннього збору |
| Robota.ua | Так само — прямого доступу немає, лише опосередковано через дані ДСЗ | **Не підтверджено напряму** — публічного read-API для агрегаторів немає |
| LinkedIn | Технічно можливий лише офіційний Jobs API за партнерською угодою | **Заборонено без партнерства** — умови використання прямо забороняють автоматичний збір вакансій |
| Lobby X | Публічний дайджест вакансій; окремого API чи RSS не знайдено | **Ручний імпорт** — варто написати напряму щодо партнерства, місія платформи близька до нашої |
| Telegram-канал «Стався, метч» (t.me/thelede) | Публічний канал: Telegram Bot API або перегляд публічної версії каналу | **Дозволено для публічних каналів** — підключається вручну адміністратором, кожен пост модерується перед публікацією |
| Detector Media | Це власні вакансії організації, а не потік чужих оголошень | **Не є джерелом-агрегатором** — додається вручну як звичайний роботодавець, а не через імпорт-конектор |

Для будь-якого джерела без підтвердженого API чи партнерства — **резервний сценарій: ручне додавання адміністратором** через адмінпанель (форма «Додати вакансію вручну з джерела X»), доки не буде підтверджено законний автоматичний спосіб.

Загальний цикл оновлення: `fetchList → diff проти вже відомих зовнішніх id → fetchDetail для нових/змінених → normalize → duplicate-check → moderation queue (якщо сумнівно) → publish/update → import_logs`.

## 6. Виявлення дублікатів

Псевдоалгоритм:

```
score = 0
+ 40, якщо нормалізовані назва посади + компанія збігаються (fuzzy match, схожість ≥ 0.85)
+ 20, якщо місто збігається
+ 15, якщо зарплатний діапазон перетинається
+ 15, якщо зовнішній ідентифікатор чи посилання вже зустрічались
+ 10, якщо дата публікації в межах ±3 днів
якщо score ≥ 70 → одна duplicate_group; обираємо основний запис:
  пряма вакансія роботодавця > вакансія з офіційного API > вакансія з дозволеного парсингу
```

Усі підтверджені джерела одного дубліката зберігаються в `imported_items`, але публічно показується один запис.

## 7. Алгоритм «Синергія» (реалізовано в прототипі як `computeMatch()` у `js/data.js`)

Ваги за замовчуванням (адміністратор може змінювати): категорія — 35, навички — 25, формат роботи — 15, рівень посади — 15, місто/дистанційність — 10. Кожен критерій додає бал і текстове пояснення; відсутність збігу — до списку `gaps`. Критичні несумісності (обов'язкова мова, формат роботи, право працювати в країні, засадничо інший рівень) виключають рекомендацію повністю, а не просто знижують бал. Результат мапиться на три рівні: висока (≥75%), можлива (≥45%), часткова (нижче). Стать, вік, фото, етнічне походження, релігія, сімейний стан, здоров'я, політичні погляди та перерви в кар'єрі **ніколи не є критеріями** — це архітектурне обмеження, а не просто політика.

## 8. Платне просування і ротація

Просунуті записи (`promoted_items`, поле `active_until`) показуються в окремому пріоритетному блоці зверху відповідної видачі **та** у звичайних результатах пошуку — але лише коли вони релевантні запиту (той самий фільтр релевантності, що й для органічних результатів). Якщо просунутих записів у видачі кілька: rotation за принципом «найдовше не показувався першим» (round-robin за `last_shown_at`), з рівномірним розподілом показів і додатковим пріоритетом записам, що завершуються раніше. Ніколи не приховує органічні результати і не гарантує конкретної кількості переглядів чи відгуків.

## 9. Платіжна архітектура

`orders` (намір оплати: послуга + сума + промокод) → провайдер (LiqPay/WayForPay/Fondy) → вебхук підтвердження → `payments` (факт оплати) → застосування ефекту (продовження строку на 30 днів або активація `promoted_items` на 7 днів) → `invoices` (фінансовий документ) → відображення в історії платежів користувача. `refunds` — окрема таблиця з причиною і статусом. Ціни, тривалість послуг, знижки та промокоди керуються з адмінпанелі (`paid_services`, `promo_codes`), а не жорстко прописані в коді.

## 10. Backlog і етапи (мапується на MVP-список зі специфікації)

**Етап 0 — фундамент:** авторизація, ролі, профілі, категорії/довідники, база даних.
**Етап 1 — контент:** створення вакансій і резюме вручну, каталоги, базовий пошук і фільтри, сторінки компаній.
**Етап 2 — CV та строки:** завантаження PDF/DOCX, розпізнавання з ручним підтвердженням, строк публікації 30 днів, архівація, нагадування.
**Етап 3 — взаємодія:** збереження записів, статуси, приватні нотатки, відгуки, підписки, центр сповіщень.
**Етап 4 — Синергія:** базовий алгоритм на структурованих полях і категоріях (без ML), пояснення рекомендацій, відхилення рекомендацій.
**Етап 5 — монетизація:** інтеграція платіжної системи, платне продовження, платне просування з ротацією, керування цінами.
**Етап 6 — імпорт:** ручний імпорт адміністратором, потім один підтверджений автоматичний конектор, виявлення дублікатів.
**Етап 7 — модерація й адмінка:** черга модерації, скарги, базова аналітика.

Кожен наступний етап залежить від фундаменту (Етап 0) і моделі даних вакансії/резюме (Етап 1); Синергія (Етап 4) залежить від наявності категорій і структурованих полів (Етап 1–2); монетизація (Етап 5) залежить від того, що вже є що продовжувати/просувати (Етап 1–2).

## 11. Критерії приймання (витяг)

- Кандидат створює, редагує, приховує й видаляє резюме; роботодавець — вакансію.
- Завантажений CV перетворюється на редаговані поля; система не додає фактів, яких немає в оригіналі.
- Вакансії й резюме автоматично архівуються через 30 днів, з нагадуванням заздалегідь.
- Платне продовження додає 30 днів; платне просування активує пріоритетний блок на 7 днів із прозорою ротацією.
- Кожна рекомендація «Синергія» має текстове пояснення і може бути відхилена користувачем; рекомендації не розкривають приховані дані.
- Імпортовані вакансії завжди містять посилання на першоджерело; дублікати не створюють окремих карток.
- Усі платежі й адміністративні дії фіксуються в журналах.

## 12. План тестування (напрямки)

- **Юніт-тести:** `computeMatch()` (усі критичні несумісності, межі рівнів відповідності), нормалізація CV-парсингу, дедуплікація.
- **Інтеграційні:** цикл імпорту джерела (fetch → normalize → duplicate-check → moderation), платіжний вебхук → продовження/просування.
- **E2E (golden path):** реєстрація кандидата → створення резюме через CV → підтвердження полів → публікація → перегляд у каталозі → отримання рекомендації «Синергія» → відгук на вакансію. Аналогічно для роботодавця: реєстрація → профіль компанії → вакансія → модерація → публікація → перегляд рекомендованих резюме.
- **Доступність:** контраст, клавіатурна навігація, alt-тексти, коректна робота зі скринрідерами (WCAG 2.1 AA).
- **Юридичний огляд перед запуском:** політика конфіденційності, згода на обробку даних, умови використання кожного джерела імпорту.
